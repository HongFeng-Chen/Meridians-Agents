# 评测 Harness 设计方案

> 位置：`go_agent/internal/biz/harness` ｜ 状态：M1 骨架已落地（本包可编译、单测通过）
> 对应调研：任务 #46「如何从 0 自研一套 harness（软件测试 / 模型评测）」

## 1. 背景与定义

**Harness（测试吊架）** 是评测领域的标准基础设施：把「被测对象」放进一个标准化的执行环境里，用固定的流程驱动它跑完一批用例，并统一采集、判分、出报告。软件测试里的 test harness 跑的是被测代码，模型评测 harness（如 OpenAI Evals、lm-eval-harness、AgentBench）跑的是被测模型 / 被测 Agent。

本系统的 harness 解决一个具体问题：**当前平台上 Agent 定义越建越多（agentfactory 已支持 13 种执行图（含 auto）+ 动态建 Agent），但改一次提示词 / 换一个模型 / 调一版执行图后，效果好不好只能靠人工发几条消息试。缺少一套可重复、可量化、可对比的回归评测机制。**

## 2. 现状盘点（harness 不重复造轮子）

评测 harness 需要的四块能力，系统里已有三块半：

| 能力 | 现状 | harness 的取舍 |
|---|---|---|
| 被测对象执行 | `agentfactory` Runtime：ReAct / Plan-Execute / Reflexion / Orchestrator 等 13 种执行图，能力白名单 + 风险评估 | **直接复用**：Agent 即被测件，黑盒调用 |
| 模型调用 | `llm.Manager` 多数据源 + 调用记录（prompt/reply/tokens 全落库） | **直接复用**：模型横评走数据源，Judge 也走它 |
| 调用可追溯 | `history.WithTask/WithConv` → op_histories；trace 事件链路 | **天然受益**：评测产生的每次调用都带 meta，链路可查 |
| 用例管理 + 判分 + 报告 | 无 | **本包新增**：`harness` 域 |

结论：harness 定位为「**考官**」，不实现任何推理循环。它只做四件事：管用例、驱动执行、判分、出报告。

## 3. 设计原则

1. **黑盒原则**：harness 对被测对象只知道 `target`（`agent:<key>` / `model:<name>`）和输入输出。被测对象的内部执行图、提示词版本变化不影响评测流程 —— 这保证「改版前 vs 改版后」可比。
2. **用例与执行分离**：用例集（Set/Case）是静态资产，运行（Run/RunItem）是动态记录。同一用例集可反复跑、可跨 target 跑（横评）。
3. **判分双轨制**：
   - **规则断言**（确定性、零成本）：contains / not_contains / regex / json_valid / min_length / max_length —— 适合有明确验收标准的用例（结构化输出、必含要点、禁止内容）；
   - **LLM-as-Judge**（语义开放题）：参考答案 + 评分要点 → 裁判模型按 JSON 协议输出 `{pass, score, reason}`。裁判输出不合规按断言失败处理 —— **评测器自己不能成为被测对象的故障源**。
   - 加权合成：用例分 = Σ通过权重 / Σ总权重 × 100；运行分 = 完成用例的平均分。
4. **异步运行**：评测一批用例可能耗时几十分钟（每例一次完整 Agent 执行）。`StartRun` 立即返回运行行，worker 池（默认并发 2）后台执行，进度实时写回 Run 行 —— 与任务中心「提交后轮询」的交互心智一致。
5. **故障隔离**：单用例超时 / 执行报错只影响该用例（Errored 计数），不拖垮整次运行；全部失败才把 Run 置为 failed。

## 4. 领域模型

```
Set 用例集 1 ──── N Case 用例            （静态资产，MySQL）
                 │
Run 运行  1 ──── N RunItem 逐例结果      （动态记录，MySQL）
  │                    │
  └ target/config      └ output / checks[] / score / latency / tokens
```

- **Set**：名称、默认 target、标签、描述。一个 Set = 一场「考试卷」。
- **Case**：`Input`（输入）+ `Context`（可选前置上下文）+ `Expect`（参考答案，Judge 用）+ `Checks[]`（断言规则）+ `Tags`（报告按维度聚合）+ `Enabled`（停用不参与）。
- **Run**：状态机 `pending → running → succeeded / failed / canceled`；进度字段 `total / done / passed / failed / errored / score / cost_ms` 实时推进。
- **RunItem**：被测对象原始输出、逐条 CheckResult（含失败原因 / Judge 评语）、单例耗时与 token 消耗。

包结构（已落地）：

```
internal/biz/harness/

├── types.go        领域类型 + 断言规则 + Score 加权算法

```

## 5. 执行流程

```
StartRun(setID, cfg)
  │  校验 target / 用例非空 → 创建 Run(pending) → 异步
  ▼
executeRun（goroutine，context 与请求解耦，支持 StopRun 取消）
  │  Run → running；DeleteItemsOfRun（重跑清旧数据）
  ▼
并发池（cfg.Concurrency，默认 2）逐例分发 ── 取消检查在用例边界
  ▼ 每例（单例超时 cfg.PerCaseTimeoutSec，默认 120s）
  ├─ ① Runner.Run(target, context+input)      ← agentfactory 同步执行 / llm 直连
  ├─ ② judge()：规则断言逐条判定 + llm_judge 裁判
  ├─ ③ 落 RunItem（output / checks / score / latency）
  └─ ④ 推进 Run 计数与均分 → SaveRun（前端可实时轮询）
  ▼ 全部完成
聚合终态：succeeded / failed（全 errored）/ canceled；记录 cost_ms
```

**与链路的关系**：Runner 适配器执行 Agent 时会把评测运行身份塞进 context（`llm.WithMeta` / `history.WithTask`，M2 接线时补 `taskID = 评测专用命名`），于是每次评测在任务中心 / 调用历史里都可追溯，token 开销按用例归集。

## 6. LLM-as-Judge 协议

```
System: 你是严格的评测裁判。根据「评分要点」判断被测输出是否合格。
        只输出 {"pass": bool, "score": 0-100, "reason": "≤100字判定依据"}
User:   题目输入 + 参考答案 + 评分要点 + 被测输出（各截断防爆上下文）
解析:   括号平衡 JSON 提取（容忍裁判输出前后缀说明文字）
降级:   裁判未接线 / 调用失败 / 输出无 JSON → 该断言按失败处理，Detail 记原因
```

要点：`temperature=0`（判分要稳定）；Judge 模型可按 Run 配置指定（`JudgeModel`），便宜的小模型跑回归、强模型跑发布前评审。

## 7. 与现有系统的接线（M2 实施）

| 端口 | 实现位置 | 说明 |
|---|---|---|
| `Repo` | `data/db/models/harness.go` + `data/db/repo/harness.go` | 四张表：`harness_sets / harness_cases / harness_runs / harness_run_items`，GORM AutoMigrate |
| `Runner` | `data/third_service/…` 或 service 层适配器 | `agent:` → `agentfactory.UseCase` 新增同步执行入口（复用 `executeTaskNow` 思路建临时任务）；`model:` → `llm.Manager` 直连 |
| `Chatter` | wire.Bind 到 `llm.Manager` | 与 agentfactory 同一绑定方式 |
| Service/API | `service/harness_service.go` + `api/harness/v1/harness.proto` | sets / cases / runs 三组 CRUD + start/stop/report，buf generate 全链路 |
| 前端 | 评测中心页（`#/harness`） | 用例集管理、启动运行（选 target / Judge 模型 / 并发）、运行进度轮询、报告页（逐例展开断言结果与 Judge 评语，复用 Markdown 渲染） |

存储分工沿用系统惯例：MySQL 存全部评测数据；Redis 可选缓存运行中 Run 快照（前端轮询高频时）；harness 本身不需要 Milvus。

## 8. 路线图

- **M1（已完成，本包）**：领域模型、执行引擎、判分双轨、单测。纯 biz 包，不接线即可独立演进。
- **M2**：Repo/PO/适配器 + proto/service + 前端「评测中心」。跑通 agent 级回归评测闭环。
- **M3**：用例集导入导出（JSONL/CSV，兼容公开评测集格式）；回归基线（每次发布前跑指定 Set，与上次 Run 逐例 diff，分数回退标红）。
- **M4**：模型横评（同一 Set 多 target 并行）；按 Tags 维度聚合报告；评测结论自动生成 Markdown 摘要；接入 CI（定式回归）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 评测打爆数据源 / 触发限流 | 并发默认 2 可配；单例超时；llm.Manager 的调用记录可按 purpose 统计开销 |
| LLM Judge 不稳定 | temperature=0；Judge 输出协议化 + 解析降级；重要场景用规则断言兜底 |
| 评测用例漂移（改了 Agent 行为导致旧断言失效） | 用例带 `Enabled` 与 `UpdatedAt`；M3 的回归基线 diff 让漂移可见而非静默 |
| 被测 Agent 副作用（评测时调用了写操作 MCP 工具） | M2 接线时约定：评测运行的身份标记进 context，风险评估 Agent 可按来源收紧策略（只放行只读工具） |
